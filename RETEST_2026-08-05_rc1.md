# Python 3.15 Data Engineering — Blocker Retest

**Author:** Dr. Ceasar Jackson Jr.
**Date:** August 5, 2026
**Baseline:** `PYTHON315_DATAENG_READINESS_ASSESSMENT.pdf` (June 5, 2026 — Python 3.15.0b1)
**Method:** PyPI wheel-tag resolution, package metadata inspection, upstream source inspection
**Tooling:** `scripts/check_cp315_wheels.py` → `reports/cp315_wheels_20260805.json`

---

## Executive finding

**One of the six June blockers has cleared. One has been resolved upstream but is
still gated by package metadata. Four are unchanged. One new exclusion has
appeared that the June assessment had not tested.**

The PyArrow wheel gap — the root of the entire cascade — is **exactly where it
was in June**. No cp315 wheels exist for PyArrow on any platform, not just macOS
ARM64.

The material change is one of timing, not of state: **CPython 3.15.0rc1 shipped
yesterday, August 4, 2026**, and the ABI is now frozen. The June assessment
predicted cp315 wheels within 2–4 weeks of an RC. That clock started yesterday.
This retest is arriving one day into the window, which is why so little has moved.

### 2.1 Delta Lake is genuinely unblocked

`deltalake 1.6.2` publishes `deltalake-1.6.2-cp310-abi3-macosx_11_0_arm64.whl`.
Because it is a **stable-ABI (abi3)** wheel built against cp310, it installs and
loads on any CPython ≥ 3.10 — including 3.15 — without upstream needing to cut a
3.15-specific build. Separately, its metadata now reads
`pyarrow>=21 ; extra == 'pyarrow'`, so PyArrow is an opt-in extra rather than a
hard dependency.

This is the one recommendation from the June report (§8.3: "when cp315 wheels
appear, re-test Dask.dataframe, Delta Lake, and MLflow") that resolved by a
different route than predicted — Delta Lake did not wait for PyArrow, it
decoupled from it.

### 2.2 Prefect — correction to the June root-cause attribution

The June assessment stated: *"Prefect 3.7.3 imports this symbol at startup…
Prefect must patch its codebase to remove the reference."*

**That attribution was incorrect.** Scanning every `.py` in both
`prefect-3.7.3` and `prefect-3.8.1` returns **zero** references to
`no_type_check_decorator`. The symbol comes from `typing_extensions`, a
transitive dependency, which re-exported it from `typing` unconditionally.

`typing_extensions 4.16.0` now guards it:

```python
# Breakpoint: https://github.com/python/cpython/pull/133602
if sys.version_info < (3, 15, 0):
    _typing_names.append("no_type_check_decorator")
    __all__.append("no_type_check_decorator")
```

So the **technical** blocker is fixed, and it was never Prefect's to fix.
What remains is a **metadata gate**: `prefect 3.8.1` declares
`Requires-Python: <3.15`, so pip on 3.15 silently resolves back to
`prefect 3.2.15`. Prefect has not yet certified 3.15, which is reasonable
one day after rc1.

**Action:** re-test Prefect on 3.15 with `--ignore-requires-python` to
determine whether the gate is now purely conservative. If it installs and runs,
that is a concrete, well-evidenced upstream issue worth filing.

### 2.3 Airflow — new finding

June deferred Airflow as "heavy optional install". It is now worth recording
that `apache-airflow 3.3.0` declares `Requires-Python: !=3.15` — an explicit,
deliberate exclusion of 3.15 specifically, not merely an untested version.
Pip on 3.15 falls back to `apache-airflow 3.0.6`. Treat orchestration as the
weakest link in the 3.15 migration story: **both** Prefect and Airflow currently
exclude it by metadata.

## 3. Correction: the core stack is source-built, not wheel-installed

This did not surface in June, and it changes the migration story.

`numpy`, `pandas`, `duckdb`, `matplotlib`, and `scipy` have **no cp315 wheels on
any platform** — macOS ARM64 or manylinux. The June report's PASS for these
packages is still accurate as a functional result, but it means `uv` compiled
them from sdist into `.venv`, not that wheels existed.

Practical consequence: the June "90% — production-grade capability" score for
the data engineering stack assumes a machine with a full C/C++ build toolchain.
That environment is **not reproducible in CI** on a slim container, and a clean
`uv sync` on a fresh box will either take a very long time or fail outright.
Worth stating explicitly in the next release notes.

### Ecosystem readiness spot-check at rc1

Of the compiled packages sampled, only **Pillow 12.3.0** publishes a genuine
`cp315-cp315` wheel today. `cryptography` rides `abi3` and is fine by accident of
build strategy rather than by 3.15 support.

**Takeaway:** projects shipping `abi3` wheels (deltalake, cryptography) crossed
the 3.15 line automatically. Projects shipping version-locked `cpXXX` wheels
(pyarrow, numpy, pandas, duckdb, ray) all still need to cut builds. That is the
single best predictor of which of your dependencies will clear next.

## 4. Method, and what is *not* verified

Findings are derived from three sources, all primary:

1. **Wheel-tag resolution** — `pip download --no-deps --only-binary=:all:` against
   an explicit `--python-version 3.15 --abi cp315 --platform macosx_*_arm64`
   target, sweeping macOS deployment targets 11 through 26 to avoid false
   negatives from exact-string tag matching.
2. **Package metadata** — `Requires-Python` and `Requires-Dist` read directly from
   the `METADATA` file inside each wheel.
3. **Upstream source** — direct inspection of `typing_extensions.py` and the full
   `prefect` wheel contents.

**Harness validation.** The probe was run against cp313 and cp314 as controls
and returned wheels for every package. A cp315 negative therefore reflects
upstream absence, not a broken harness.

**A trap worth recording:** `pip download --abi cp315` does **not** restrict
results to cp315 wheels. Pip will satisfy the request with a `py3-none-any` or
`cpXX-abi3` wheel, both legitimately installable. Reading only pip's exit status
produces false positives — an early pass of this retest wrongly scored `ruff`,
`cryptography`, and `pydantic-core` as having cp315 wheels when none of the three
does. `scripts/check_cp315_wheels.py` parses the returned filename and classifies
it as `native` / `abi3` / `pure` / `none` for exactly this reason.

### Not verified

**No runtime testing was performed.** A Python 3.15 interpreter could not be
provisioned in the analysis environment (the python-build-standalone download
host was unreachable), so nothing here was confirmed by actually importing a
module on 3.15. Specifically unverified:

- Whether `prefect 3.8.1` actually runs on 3.15 with its metadata gate bypassed.
- Whether `deltalake 1.6.2` functionally works on 3.15 beyond installing.
- Whether the b1→rc1 delta introduced any new stdlib breakage.

These require running `scripts/validate_extended.py` on your local 3.15.0rc1 venv.

## 5. Recommended next actions

1. **Upgrade the venv from b1 to rc1.** The ABI is frozen; anything that builds
   now will keep working through GA. Then re-run `bash scripts/validate_all.sh`.
2. **Re-run Phase 7 benchmarks on rc1.** The JIT changes are large enough
   (~12–13% on AArch64 macOS) that the June Pandas/Polars numbers no longer
   describe the runtime you are on.
3. **Add Delta Lake to the passing set** — it is the one genuine win since June.
4. **Test Prefect with `--ignore-requires-python`** to separate "technically
   broken" from "not yet certified", and file upstream if it is the latter.
5. **Re-run the wheel probe weekly through GA:**
   ```bash
   python scripts/check_cp315_wheels.py --json reports/cp315_wheels_$(date +%Y%m%d).json
   ```
   Exit code 1 means at least one package is still blocked, so this drops
   straight into a cron job or CI gate.
6. **Revise the readiness score with the source-build caveat.** The 90% figure
   should carry an explicit note that it depends on a local build toolchain.
